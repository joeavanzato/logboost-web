## Summary

This phase has three distinct concerns: (1) Dockerfile modification to download and bundle the LogBoost Linux binary at image build time, (2) docker-compose.yml change to remove the binary volume mount, and (3) a significant rewrite of the admin Setup page to replace the old "Download from GitHub" form with a Docker-aware status card and "Check for Updates" workflow.

The GitHub release structure is confirmed. Tag `prod_1_5_0` is the current latest. The release asset `logboost_linux_amd64.zip` (5.8 MB) is available at a stable, direct URL. The binary inside is almost certainly named `logboost` (Go convention for Linux: lowercase, no extension), but this cannot be verified without extracting the zip — the existing admin.py already probes for both `logboost` and `LogBoost` so the code is safe regardless.

The Python codebase already uses `urllib.request` (stdlib) for HTTP in `download_logboost()` and `requests` (third-party, already in requirements.txt) throughout `app.py`. For the GitHub API update check, `requests` is the right tool — it is already a dependency. For the Dockerfile binary download, `curl` is already installed in the image and is the correct tool (avoids adding a new apt package).

**Primary recommendation:** Bundle via `curl | unzip` in a single Dockerfile RUN layer. Use `requests` for the GitHub API check. Store the bundled version tag as a constant in admin.py. Store last-checked timestamp and cached GitHub version in SQLite `settings` table (already exists). Update binary by downloading to `/data/bin/logboost` (user-writable volume) and updating `LOGBOOST_PATH` env override, rather than overwriting the root-owned `/usr/local/bin/logboost`.

## Architecture Patterns

### Dockerfile: Binary Download in Single RUN Layer

**What:** Download zip, extract binary, install to `/usr/local/bin/logboost`, clean up — all in one `RUN` command.
**Why single layer:** Intermediate files (zip) don't appear in the image. Consistent with existing pattern (build-essential purged in same RUN as pip install).
**Where to add:** After the `useradd` step but before `USER logboost` (root required for write to `/usr/local/bin/`).

```dockerfile
# Source: Docker best practices - single RUN for download+install+cleanup
ARG LOGBOOST_VERSION=prod_1_5_0
RUN apt-get update && apt-get install -y --no-install-recommends unzip \
    && curl -fsSL \
       "https://github.com/joeavanzato/LogBoost/releases/download/${LOGBOOST_VERSION}/logboost_linux_amd64.zip" \
       -o /tmp/logboost.zip \
    && unzip /tmp/logboost.zip -d /tmp/logboost_extracted \
    && find /tmp/logboost_extracted -type f \( -name "logboost" -o -name "LogBoost" \) \
       -exec install -m 0755 {} /usr/local/bin/logboost \; \
    && rm -rf /tmp/logboost.zip /tmp/logboost_extracted \
    && apt-get purge -y --auto-remove unzip \
    && rm -rf /var/lib/apt/lists/*
```

**Note on binary name:** The zip contents cannot be verified without extraction. The `find` command handles both `logboost` and `LogBoost` binary names. Based on Go conventions for Linux, the binary is expected to be named `logboost` (lowercase).

**Note on `ARG`:** Using `ARG LOGBOOST_VERSION=prod_1_5_0` allows the version to be overridden at build time (`docker build --build-arg LOGBOOST_VERSION=prod_1_6_0`) without changing the Dockerfile. This is the locked decision to pin to `prod_1_5_0` as default.

### Version Detection: Bundled vs. Updated

The bundled version is known at build time (`prod_1_5_0`). After an update, the binary is at `/data/bin/logboost`. Two sources of truth:

1. **Bundled version:** Hardcoded constant `BUNDLED_LOGBOOST_VERSION = "prod_1_5_0"` in admin.py
2. **Override path:** SQLite setting `logboost_override_path` — if set, the override binary is in use
3. **Current effective version:** SQLite setting `logboost_installed_version` — updated after a successful download

**Version comparison:** The tag format is `prod_X_Y_Z`. Simple string comparison is insufficient. Extract numeric parts: `prod_1_5_0` → `(1, 5, 0)` tuple. Compare tuples — no third-party library needed. The `packaging` library is NOT in requirements.txt and should not be added for this simple case.

```python
# Version comparison — no third-party library needed
def _parse_logboost_tag(tag: str) -> tuple[int, ...]:
    """Parse 'prod_1_5_0' -> (1, 5, 0). Returns (0,) on parse failure."""
    try:
        parts = tag.replace('prod_', '').split('_')
        return tuple(int(p) for p in parts)
    except (ValueError, AttributeError):
        return (0,)

def is_newer_version(latest_tag: str, current_tag: str) -> bool:
    return _parse_logboost_tag(latest_tag) > _parse_logboost_tag(current_tag)
```

### GitHub API: Check for Updates

**Endpoint:** `GET https://api.github.com/repos/joeavanzato/LogBoost/releases/latest`
**Returns:** JSON with `tag_name` field containing `"prod_1_5_0"` (latest tag)
**Rate limit:** 60 requests/hour unauthenticated (source: GitHub official docs)

```python
# Source: GitHub REST API docs - https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api
import requests

def check_github_latest() -> dict:
    """Query GitHub releases API for latest LogBoost version.

    Returns dict with keys: tag_name, html_url, error (if any)
    """
    url = 'https://api.github.com/repos/joeavanzato/LogBoost/releases/latest'
    try:
        resp = requests.get(url, timeout=10, headers={'Accept': 'application/vnd.github+json'})
        if resp.status_code == 403:
            remaining = resp.headers.get('x-ratelimit-remaining', 'unknown')
            return {'error': f'GitHub API rate limited (remaining: {remaining})'}
        resp.raise_for_status()
        data = resp.json()
        return {
            'tag_name': data.get('tag_name', ''),
            'html_url': data.get('html_url', '')
        }
    except requests.exceptions.RequestException as e:
        return {'error': str(e)}
```

**Caching recommendation (Claude's Discretion):** Store result in SQLite settings as `github_latest_version` and `github_latest_checked` (ISO timestamp). On "Check for Updates" click, always query live (user-initiated, not frequent). The 60/hour rate limit is not a concern for manual-only checks.

### Update Download: Write to `/data/bin/logboost`

The container runs as `logboost` (UID 1000). `/usr/local/bin/logboost` is root-owned and cannot be overwritten at runtime. `/data/` is owned by UID 1000 (set by `chown -R logboost:logboost /data` in Dockerfile).

**Override binary location:** `/data/bin/logboost`
The `/data/bin/` subdirectory must be created in the Dockerfile:
```dockerfile
RUN mkdir -p /data/maxmind /data/intel /data/cache /data/config /data/db /data/bin \
    && chown -R logboost:logboost /data
```

After download, the app updates `LOGBOOST_BINARY` at runtime (already done for path changes: `global LOGBOOST_BINARY`). The effective binary path becomes `/data/bin/logboost` and is stored as `logboost_override_path` in settings.

**How `/health` works with override:** The health endpoint reads `LOGBOOST_PATH` env var → checks `Path(LOGBOOST_BINARY).exists()`. After update, admin must store override path and the app must prefer it. See Architecture Pattern below.

### `LOGBOOST_BINARY` Priority Order

The effective binary path must follow this priority:
1. `/data/bin/logboost` if `logboost_override_path` setting exists AND file exists
2. `LOGBOOST_PATH` env var (default: `/usr/local/bin/logboost`, the bundled binary)

This priority should be determined at module load time in `admin.py` (mirroring how `LOGBOOST_BINARY` is set now) but also refreshed after a successful update download.

### Anti-Patterns to Avoid

- **Do NOT `chmod +x` in a Python subprocess at runtime:** Use `os.chmod(path, 0o755)` instead.
- **Do NOT use `ADD` in Dockerfile for URL downloads:** Docker recommends `curl` + `RUN` over `ADD` with URL (security concern: no checksum verification; behavior is opaque).
- **Do NOT write to `/usr/local/bin/` at runtime:** Container runs as UID 1000 (non-root). Writing to `/data/bin/` is the correct override location.
- **Do NOT use `requests` at import time for version checks:** Only query GitHub when user clicks "Check for Updates" — no startup delay.
- **Do NOT break the global `LOGBOOST_BINARY` mutation pattern:** The existing `global LOGBOOST_BINARY` pattern in `set_logboost_path()` works and should be replicated for the override path.

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Semantic version comparison | Custom regex parser | Simple `tuple(int(p) for p in tag.split('_')[1:])` comparison | LogBoost tags are `prod_X_Y_Z` — numeric tuple comparison is sufficient; no `packaging` library needed |

**Key insight:** This phase is plumbing work. The hard parts (HTTP client, settings, zip extraction) all have existing solutions already in the project. Do not introduce new dependencies.

## Common Pitfalls

### Pitfall 1: `/usr/local/bin/logboost` Cannot Be Overwritten at Runtime

**What goes wrong:** Update download code tries to write to `/usr/local/bin/logboost` and gets `PermissionError: [Errno 13] Permission denied`. Container runs as UID 1000 (`logboost` user). The bundled binary at `/usr/local/bin/logboost` is owned by root (installed during build as root).

**Why it happens:** The Dockerfile installs the binary as root (before `USER logboost`). `/usr/local/bin/` is root-owned. The container runs as the non-root `logboost` user after `USER logboost`.

**How to avoid:** Write updated binary to `/data/bin/logboost`. The `/data` tree is chowned to UID 1000. Add `/data/bin/` to the `mkdir -p` in the Dockerfile.

**Warning signs:** Any code that does `open('/usr/local/bin/logboost', 'wb')` will fail silently if the error is swallowed.

### Pitfall 2: `unzip` Not in `python:3.12-slim`

**What goes wrong:** Dockerfile RUN fails with `/bin/sh: unzip: not found` or `E: Unable to locate package unzip`.

**Why it happens:** `python:3.12-slim` is intentionally minimal. `unzip` is not pre-installed.

**How to avoid:** Install `unzip` in the same RUN layer as the download. Purge it afterward to keep the image lean (same pattern as `build-essential`).

```dockerfile
RUN apt-get update && apt-get install -y --no-install-recommends unzip \
    && ... download and extract ... \
    && apt-get purge -y --auto-remove unzip \
    && rm -rf /var/lib/apt/lists/*
```

### Pitfall 3: Binary Execute Permission Not Set

**What goes wrong:** Binary downloads successfully but `subprocess.run(['/data/bin/logboost', ...])` fails with `PermissionError: [Errno 13]` or `OSError: [Errno 8] Exec format error`.

**Why it happens:** Downloaded file may not have execute bit set. Python's `zipfile.extractall()` does not preserve Unix permissions from zip metadata by default.

**How to avoid:** After extraction, explicitly set execute permission:
```python
import os
os.chmod('/data/bin/logboost', 0o755)
```

For the Dockerfile RUN layer, use `install -m 0755` (shown in Architecture Patterns) or `chmod +x` in the same RUN.

### Pitfall 4: GitHub API Rate Limit on 403

**What goes wrong:** GitHub returns HTTP 403 for unauthenticated requests that exceed 60/hour from the same IP. The `requests.raise_for_status()` raises `HTTPError` which surfaces as a generic error to the user.

**Why it happens:** 60 requests/hour per IP for unauthenticated GitHub API calls (confirmed from official docs). In a shared NAT environment, multiple users behind the same IP share the limit.

**How to avoid:** Check for 403 specifically before `raise_for_status()`. Return a user-friendly message: `"GitHub API rate limited. Try again in an hour."` Cache the last successful result in SQLite to avoid redundant checks.

### Pitfall 5: docker-compose.yml Volume Mount Left in Place

**What goes wrong:** After removing the binary volume mount from docker-compose.yml, `docker compose up` still uses old compose config. Or worse: the mount is left in place, shadowing the bundled binary with a non-existent host path, causing `/health` to report `logboost_available: false`.

**Why it happens:** The existing compose file has: `- /opt/logboost/logboost:/usr/local/bin/logboost`. If the host file doesn't exist, Docker silently mounts an empty directory or fails to mount — behavior depends on bind mount vs. file mount semantics.

**How to avoid:** Remove the binary mount line from docker-compose.yml. Document in `.env.example` comments that the binary is now bundled. Verify with `docker inspect` that no mount exists at `/usr/local/bin/logboost` after update.

### Pitfall 6: `LOGBOOST_BINARY` Global Not Updated After Runtime Install

**What goes wrong:** User clicks "Download & Install". Download succeeds to `/data/bin/logboost`. But `run_logboost()` in `app.py` still uses the old `LOGBOOST_BINARY` global (set at module import time from `LOGBOOST_PATH` env var).

**Why it happens:** `LOGBOOST_BINARY` is a module-level global set once at startup. The existing `set_logboost_path()` route already updates it via `global LOGBOOST_BINARY` — this pattern must be replicated in the update install handler.

**How to avoid:** After writing `/data/bin/logboost`, import and update the globals in both `admin.py` and `app.py`. Or better: make `run_logboost()` read from a function (not module global) that checks settings at call time. The simplest approach that matches existing patterns: update both module-level `LOGBOOST_BINARY` globals (admin.py and app.py each have their own copy).

### Pitfall 7: `entrypoint.sh` WARN for Missing Binary Still Triggers After Bundling

**What goes wrong:** After bundling the binary, the entrypoint still warns "LogBoost binary not found" on startup even though the binary is there.

**Why it happens:** The entrypoint.sh checks `${LOGBOOST_PATH:-/usr/local/bin/logboost}`. If this is correct and the binary was installed to `/usr/local/bin/logboost` in the image, the warning should NOT trigger. But if the Dockerfile install step fails silently, the warning appears without a build error.

**How to avoid:** Add a build-time verification: after the download/install RUN, add a separate RUN to verify:
```dockerfile
RUN test -f /usr/local/bin/logboost && test -x /usr/local/bin/logboost
```
This causes the build to fail with a clear error if the binary wasn't installed correctly.

### Verified: GitHub API Check (requests, already in requirements.txt)

```python
# Source: GitHub REST API docs (https://docs.github.com/en/rest)
import requests

BUNDLED_LOGBOOST_VERSION = "prod_1_5_0"
GITHUB_RELEASES_API = "https://api.github.com/repos/joeavanzato/LogBoost/releases/latest"

@admin_bp.route('/api/setup/check-update')
@admin_required
def check_logboost_update():
    """Query GitHub for latest LogBoost version and compare with installed."""
    try:
        resp = requests.get(
            GITHUB_RELEASES_API,
            timeout=10,
            headers={'Accept': 'application/vnd.github+json'}
        )
        if resp.status_code == 403:
            remaining = resp.headers.get('x-ratelimit-remaining', 'unknown')
            return jsonify({'error': f'GitHub API rate limited. Remaining: {remaining}'}), 429
        resp.raise_for_status()
        data = resp.json()
        latest_tag = data.get('tag_name', '')

        # Cache in settings
        set_setting('github_latest_version', latest_tag)
        set_setting('github_latest_checked', datetime.now().isoformat())

        installed_version = get_setting('logboost_installed_version', BUNDLED_LOGBOOST_VERSION)
        update_available = _is_newer_logboost_tag(latest_tag, installed_version)

        return jsonify({
            'latest_tag': latest_tag,
            'installed_version': installed_version,
            'update_available': update_available,
            'release_url': data.get('html_url', ''),
            'checked_at': datetime.now().isoformat()
        })
    except requests.exceptions.RequestException as e:
        return jsonify({'error': str(e)}), 500


def _is_newer_logboost_tag(latest: str, current: str) -> bool:
    """Compare prod_X_Y_Z tags. Returns True if latest > current."""
    def parse(tag: str) -> tuple:
        try:
            return tuple(int(p) for p in tag.replace('prod_', '').split('_'))
        except (ValueError, AttributeError):
            return (0,)
    return parse(latest) > parse(current)
```

### Verified: Runtime Update Install

```python
# Source: Project patterns in admin.py (download_logboost, set_logboost_path)
import zipfile
import io
import os

@admin_bp.route('/api/setup/install-update', methods=['POST'])
@admin_required
def install_logboost_update():
    """Download latest LogBoost binary to /data/bin/logboost."""
    latest_tag = get_setting('github_latest_version')
    if not latest_tag:
        return jsonify({'error': 'Run Check for Updates first'}), 400

    asset_url = f"https://github.com/joeavanzato/LogBoost/releases/download/{latest_tag}/logboost_linux_amd64.zip"
    install_path = '/data/bin/logboost'

    try:
        resp = requests.get(asset_url, timeout=120)
        resp.raise_for_status()

        with zipfile.ZipFile(io.BytesIO(resp.content)) as zf:
            # Find the binary inside the zip
            binary_entry = next(
                (n for n in zf.namelist() if n.lower().endswith(('logboost', 'logboost.linux'))),
                None
            )
            if not binary_entry:
                return jsonify({'error': 'Binary not found in zip'}), 500

            os.makedirs('/data/bin', exist_ok=True)
            with open(install_path, 'wb') as f:
                f.write(zf.read(binary_entry))

        os.chmod(install_path, 0o755)

        # Update globals and settings
        global LOGBOOST_BINARY
        LOGBOOST_BINARY = install_path
        set_setting('logboost_override_path', install_path)
        set_setting('logboost_installed_version', latest_tag)

        return jsonify({'success': True, 'path': install_path, 'version': latest_tag})

    except requests.exceptions.RequestException as e:
        return jsonify({'error': f'Download failed: {str(e)}'}), 500
    except Exception as e:
        return jsonify({'error': str(e)}), 500
```

## Open Questions

1. **Binary name inside `logboost_linux_amd64.zip`**
   - What we know: Go convention for Linux is lowercase no extension (`logboost`). The existing admin.py probes `['LogBoost.exe', 'LogBoost', 'logboost', 'logboost.exe']`. The zip filename is `logboost_linux_amd64.zip` (lowercase prefix).
   - What's unclear: Exact filename inside the zip without downloading and extracting it.
   - Recommendation: Use `find -name "logboost" -o -name "LogBoost"` in the Dockerfile RUN (already shown in code examples). Use a `next(n for n in zf.namelist() if ...)` search for the runtime update. If neither name is found, the build fails loudly (the `test -x` verification step catches it).

2. **`LOGBOOST_BINARY` global in `app.py` vs `admin.py` — two separate copies**
   - What we know: `app.py` line 105: `LOGBOOST_BINARY = os.environ.get('LOGBOOST_PATH', 'LogBoost')`. `admin.py` line 34: `LOGBOOST_BINARY = os.environ.get('LOGBOOST_PATH', 'LogBoost')`. These are independent module-level variables.
   - What's unclear: How to update both after a runtime install, since `global` only affects the module it's in.
   - Recommendation: The simplest solution is to make `app.py`'s `run_logboost()` function look up the effective binary path from settings at call time (not the module global). This is a one-line change and eliminates the two-global problem entirely. Alternatively, export a `get_effective_logboost_path()` function from `admin.py` and call it from `app.py`.

3. **`/data/bin/` directory creation**
   - What we know: The existing Dockerfile creates `/data/maxmind /data/intel /data/cache /data/config /data/db` but NOT `/data/bin`.
   - What's unclear: Whether `/data/bin` needs to pre-exist in the image or can be created at runtime.
   - Recommendation: Add `/data/bin` to the existing `mkdir -p` line in the Dockerfile to ensure it exists and is chowned to UID 1000 from the start. This matches the existing pattern.
